# 密度分 → 置信度 → 证据强度 → 状态，全链路怎么算的

一条评论的分数不是算完就完了，会一路"滚"到表2问题档案的状态上：

```
单条评论：密度分(0-100) → 置信度(A/B/C/D)
              ↓ 按问题ID聚合成一组证据
一个问题：这组证据的置信度分布 → 证据强度(s) → 状态
```

前半段（表1_评论库里的三列）先分清楚职责：

| 列 | 类型 | 职责 |
|---|---|---|
| **密度分**（density） | 0-100 数字 | 原始分——这条评论对"复现"的贡献有多大 |
| **线索标签**（signals） | 若干个中文词 | 密度分的"来源明细"——具体命中了哪几类信号 |
| **置信度**（grade） | A/B/C/D 一个字母 | 把密度分（+是否噪音）分桶后的最终决策值 |

三者的关系：**密度分是原始分，线索标签是明细，置信度是分桶后的结论**。下游所有统计
（证据强度公式、主/次证据判定、进不进复现队列）只认置信度这个字母，不直接用密度分——
密度分和线索标签是给想深挖"为什么这条评论算 A"的人看的。

代码全部在 `scripts/confidence.py`（评分）+ `scripts/classify.py`（噪音判定、调用入口）。

## 密度分怎么算（`confidence.score()`）

基础信号权重表（跟 SKILL.md「信息密度分级」一致）：

| 信号 | 权重 | 例子 |
|---|---|---|
| control 对照实验 | 30 | "用 MX Player 放同一个文件就没事"、"以前不这样，更新后才有" |
| workaround 规避手段 | 25 | "切到软解就好了"、"清缓存/重装能解决" |
| metric 精确数值 | 20 | "下载到 97% 停"、百分比/秒数/分辨率/版本号 |
| trigger 触发条件 | 15 | "快进的时候"、"退到后台再回来就…" |
| target 技术标的 | 10 | 提到具体芯片/系统版本/协议名（蓝牙/OTG/SD卡等） |
| frequency 频率 | 10 | "每次都""偶尔"这类出现频率描述 |
| temporal 时间/版本锚点 | 10 | "最近""上次更新后"这类圈定回归范围的表达 |

命中一条信号词表里的正则就记一次，权重累加。此外还有**组合加成**：

- 同时命中 metric + trigger → **+10**（有精确数值又有触发条件，能直接写成断言）
- 同时命中 control + (trigger/metric/target 任一) → **+10**（对照实验 + 具体条件 = 变量已经被用户控制住了）
- 命中信号种类数 ≥4 个 → **+10**（多维线索交叉，可信度更高）
- 命中了具体二级分类（不是笼统未细分）→ **+5**
- 文本长度 ≥120 字符 → **+5**；<25 字符 → **-10**（太短的评论线索密度天然打折）

最终结果 clamp 到 `[0, 100]`。

## 线索标签是什么

就是上面信号表里**命中了的那几类**，用中文名列出来（`SIGNAL_CN` 映射）：

```
control→对照   workaround→规避   metric→数值
trigger→触发   target→标的       frequency→频率   temporal→锚点
```

一条评论可以同时命中好几个标签，全部列在「线索标签」列里，逗号分隔。用这一列筛选很好用：
筛「对照」能一次找出所有用户自己做过对比实验的证据（这类证据密度分天然最高，见上面 control=30）。

## 置信度怎么分桶（`confidence.grade()` + `classify.py` 的噪音判定）

**D 只看是不是噪音，不看密度分**——只要判定为噪音，不管密度分多高，直接是 D：

| 噪音类型 | 判定条件 |
|---|---|
| `tooshort` | 文本 ≤3 字符，或整条只有符号/数字 |
| `praise` | 命中夸赞类开头词（"很好用""棒"这类） |
| `rant` | 命中骂人类开头词，**且没提到任何具体功能词**（纯情绪发泄，没有指向；如果骂人但提了具体功能，比如"垃圾，声音都没有"，不算噪音，会被保留） |
| `no_signal` | 低星（≤3★）短评论（<45字符），既不像投诉也没提任何功能词——判"没有有效信息" |

⚠️ 这跟 SKILL.md「六个关键设计」里"4-5★ 只认强信号"是两回事：4-5★ 评论没命中 `complaint.STRONG`
会在分类阶段被直接清空分类（不算任何问题），这是**分类前置的门控**；这里的噪音判定是**评分阶段**的独立
逻辑，两者都会导致这条评论"不算数"，但触发条件和阶段不同。

不是噪音的情况下，按密度分 `s` 分桶：

| 密度分区间 | 置信度 | 含义 |
|---|---|---|
| `s ≥ 50` | **A** | 高置信-可直接尝试复现 |
| `25 ≤ s < 50` | **B** | 中置信-需聚合同类证据 |
| `s < 25` | **C** | 低置信-仅作计数/趋势 |
| （噪音） | **D** | 无效-噪音或零信息，过滤掉不进表 |

## 为什么这么设计

- **D 只给噪音，不给低分**——"有真实症状但零线索"的评论（比如就一句 `buffering too much`）
  密度分很低，但它不是 D，是 **C**。C 的价值是"计数器"：证明这个问题真实存在、发生了多少次，
  哪怕没法直接拿它去复现。如果按分数硬切 D，会把这批"证明问题规模"的证据一起丢掉，问题看起来
  比实际更小。
- **置信度是唯一的决策字段**——下游「证据强度」公式（`A×5 + B×2 + C×1`）、主/次证据判定、
  要不要进复现队列，全部只认这个字母，不重新看密度分数字。这样统计口径统一，不会出现"两条都是
  B 档但密度分一个48一个26，权重却算得不一样"这种不一致。密度分和线索标签留着，是给人工复核时
  想搞清楚"这条为什么被判成 A"用的明细，不参与自动统计。

## 置信度之后：怎么滚成表2的「证据强度」

表1 是**逐条评论**打分（密度分→置信度），表2 是**按问题ID聚合**之后再算一遍——聚合的输入
只有置信度这个字母，密度分数字到这一步就不再参与计算了。代码在 `scripts/build_issues.py`。

### 第一步：分主证据 / 次证据

一条评论可能同时命中好几个问题（比如一句话里既说了卡顿又说了没声音）。按问题ID分组时：

- 评论**主要在说**的那个问题 → 算这个问题的**主证据**
- 评论**顺带提到**的其他问题 → 算那个问题的**次证据**，权重打对折——因为一条评论命中多个
  关键词，越往后越可能是误报（比如吐槽卡顿时随口提了一句广告，不代表这条评论是在"报告"广告问题）

### 第二步：证据强度公式

```
s = 主证据(A档数×5 + B档数×2 + C档数×1) + 次证据同式 // 2
```

D档在表1阶段就已经被过滤掉，根本不会进这一步的聚合（不占分母，也不占分子）。

举例：某个问题下聚了 3条主证据A档 + 2条主证据B档 + 1条次证据A档：
```
s = (3×5 + 2×2) + (1×5)//2 = 19 + 2 = 21
```

**为什么只用置信度字母、不用密度分数字直接加总**：置信度已经是"分桶"后的结论（比如密度分52和98
都是A档），如果证据强度直接拿密度分数字相加，一条密度分98的孤例就能把强度拉到跟5条密度分52的
证据差不多，会让"单条证据的运气"盖过"多条证据的一致性"——按字母分桶再加权，本质是在说"我只信任
桶的判断，不信任桶内部数字的精确程度"（密度分的评分本身是关键词匹配打出来的估计值，不是精确测量）。

### 第三步：证据强度 → 状态

`s` 算出来之后，同一个「一级::二级分类」分组按下面这条判定链决定状态（命中即止）：

| 顺序 | 命中条件 | 状态 |
|---|---|---|
| 1 | 二级分类="（笼统未细分）" 且该组 A档+B档=0 | `笼统池-仅跟趋势` |
| 1′ | 二级分类="（笼统未细分）" 且该组 A档+B档≥1 | `笼统池-已有可用线索` |
| 2 | 二级分类命中 `taxonomy.py` 的 `POLICY_L2`（人工标出的"产品策略类"，如广告/付费类投诉，不是bug） | `非缺陷-产品策略` |
| 3 | `s ≥ 20` 且主证据 A档数 ≥ 2 | `线索收敛中-建议复现` |
| 4 | `s ≥ 10`（不满足条件3） | `待确认` |
| 5 | 其余（`s < 10`） | `证据不足-观察中` |

这5种（含笼统池2种）都是脚本自动判定，每次 `run_all.py` 刷新都重算；另外4个人工专属状态
（可复现-已提单/已修复待验证/已关闭/无法复现-挂起）脚本永不生成，出现即说明是人改的，
upload 时会保留（完整状态机图见 `references/sheet-schema.md`）。

⚠️ **状态不是单向递增的**——判定只看当期重算的 `s` 和主证据A档数，跟上一轮状态无关。如果这一轮
误报被清出去、或者新增了一堆低密度证据把 A档占比拉低，`s` 跌破 20，状态会从「线索收敛中-建议
复现」退回「待确认」甚至「证据不足-观察中」，不是"一旦收敛就不会退步"。

### 三个字段串起来看

| 字段 | 粒度 | 值 | 谁在用 |
|---|---|---|---|
| 密度分 | 单条评论 | 0-100 | 人工复核明细，不参与下游统计 |
| 置信度 | 单条评论 | A/B/C/D | 参与证据强度公式的**唯一输入** |
| 证据强度 s | 一个问题（聚合后） | 数字 | 决定状态判定链走到哪一条分支 |
| 状态 | 一个问题 | 5种自动+4种人工 | 决定这个问题进不进复现队列、要不要人工介入 |

一条评论的信息密度，最终只会以"是A还是B还是C"这一个比特位的精度，影响到它所在问题的状态——
中间的密度分数字、命中了哪几个线索标签，都只是这个判断过程留下的"可解释性"痕迹。
