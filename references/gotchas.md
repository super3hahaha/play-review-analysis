# 踩过的坑

## 数据
- **Play Console 导出的 CSV 是 UTF-16LE**，不是 UTF-8。`open(f, encoding='utf-16')`。
- **缺陷系统(Mantis类)导出的历史bug CSV 是 UTF-8 with BOM**，跟评论CSV编码不一样。`open(f, encoding='utf-8-sig')`。
- 历史bug的「摘要」列开头总带版本/复现频率噪音前缀，形如 `#bug2.9.1A 必现 -- ` / `.#bug_1.3.5.1 随机 --- `，
  格式不统一（有无`_`、有无开头`.`、`-`数量1~3个都有），清洗要用宽松正则 `^\.?#?bug[_ ]?[\w.]*\s*(必现|偶现|随机|建议|反馈|需求)?\s*-{1,3}\s*`，
  见 `scripts/classify_history_bugs.py`。分类匹配要在**清洗前**的原文上跑，清洗只用来生成展示用的干净摘要——
  前缀里偶尔混进标签词（比如 `【埋点】`就在前缀噪音之外，但别假设所有信号词都在前缀之后）。
- **表4分类关键词碰撞清单**：taxonomy.py 的词表是照多语言评论文本调的，搬到内部bug摘要(中文黑话/工程用语)上会有系统性误伤，
  不是零星个例，是整类整类地错。逐条人工核对 423 条候选后砍掉 130 条、修剪 18 条(见 `manual_review_history_bugs.py`)，主要模式：
  | 关键词 | 内部bug里的真实含义 | 撞上的taxonomy分类 |
  |---|---|---|
  | 版本号后缀里的字母(如 `2.3.4K`) | 就是版本号，不是"4K视频" | 格式兼容·无法播放高分辨率视频（已在classify_history_bugs.py改成清洗后文本匹配修复） |
  | `youtube`(裸词) | 播放页内嵌Youtube功能，跟"下载"无关 | 下载器·无法下载YouTube（18条里只有1条是真的） |
  | `遮挡` | UI元素互相遮挡(弹窗/导航栏/状态栏) | 广告体验·广告影响操作（本来判"广告挡住按钮"，内部bug几乎从不是这个意思） |
  | `很多`/`每次` | 各种别的频率描述 | 广告体验·抱怨有广告/数量多（本来判"广告出现太频繁"） |
  | `外置` | 外置字幕(external subtitle) | 文件管理·外置存储/SD卡/U盘文件识别问题（本来判"外部存储设备"，两个"外置"完全是两码事） |
  | `翻译` | UI文案本地化、会员状态、IAP流程 | 字幕·字幕翻译功能异常/不支持语言（本来判"字幕翻译内容错误"，内部bug里"翻译"泛指一切本地化工作） |
  → 结论：这套词表只适合评论文本，**不要直接把它当成内部bug分类器复用**；真要复用，必须逐条人工过一遍，不能只信关键词命中。
- **人工核对"先想后写"两步走会漏**：第一轮精筛时脑子里对着423条逐条判断，判完再统一转成 DROP/TRIM 字典，
  结果有3条(0188076整条该丢/0049387该摘标签/0049418该摘标签)判断做了但没写进代码，混进了"最终"结果里，
  被用户从截图里当场抓包（表现为"匹配问题档案二级分类"已经改了，但"候选关联ISS"没同步重算，两个字段互相矛盾）。
  → 教训：①人工核对类任务，判断和编码要在同一步完成，不要"先通读一遍出结论、再回头转成代码"；
  ②任何从标签衍生出来的字段(如候选关联ISS)必须每次从**当前**标签集合重新计算，不能读取上一轮的旧值——
  这是比"少判断几条"更容易踩的坑，因为它不会报错，只会安静地留下自相矛盾的数据。
- **只信二级分类标签的字面意思，不够——要去查该分类对应ISS的真实评论原文核对**：
  "文件管理·文件重复显示"表面上望文生义很像"Duplicate Files 清理器工具"的bug，实际上对应的 ISS-077
  关联的真实评论(R20980/R28916)讲的是"一个文件被扫描/显示bug误判成两份"，跟清理器工具完全是两回事——
  全部5条历史bug匹配整类判断错误，而且是**标签语义理解错了**，不是关键词正则误伤(那种问题至少还能靠
  重新读关键词发现，这种连人工判断的第一直觉都会中招)。
  → 以后二级分类只要不是"崩溃/ANR"这种毫无歧义的词，匹配前先按 `表2的关联评论ID → 表1原文` 查2条真实
  评论，用真实症状定标签的准确含义，不要单凭二级分类的中文名字面推断。

## 表1/表2 筛选口径必须一致，否则「关联评论ID」里混进查不到的幽灵ID（2026-09 发现）
- `build_issues.py` 统计证据时，高星（4-5★）评论只要求 `primary` 有值，**不看 `grade`**；
  但 `export_sheets.py` 生成表1 时，高星评论曾要求 `grade in ('A','B')` 才导出——两边标准不一样，
  导致 grade=C 的高星强信号证据被表2 计入证据、写进「关联评论ID」，却**永远不会出现在表1 里**，
  用户点这个ID对应的行时查无此人，而且**重跑 `run_all.py` 多少次都不会自愈**（不是缓存过期，
  是两个脚本的筛选逻辑本身不一致）。
- `grade='D'` 是 `confidence.py:grade()` 里专门留给 `noise` 的（见该函数注释"D 只给噪音"），
  C 是"低置信但非噪音"的合法计数器证据（`GRADE_DESC['C'] = "低置信-仅作计数/趋势"`），不是垃圾，
  不该跟 D 一起被过滤掉。**修复**：`export_sheets.py` 的高星筛选条件从 `grade in ('A','B')`
  改成 `grade != 'D'`，跟低星筛选（`not noise`）保持同一个"只排除真噪音"的口径。
- **顺手加了断言**（`export_sheets.py` 末尾 `check_sheet2_ids_exist_in_sheet1()`）：每次跑完
  `run_all.py` 自动核对表2 引用的每个评论ID 是否都能在刚生成的表1 里查到，查不到直接打印
  `✗ 一致性检查失败` 并点名具体缺失哪几个ID——这类"两个脚本筛选条件本该一致却写岔了"的坑，
  光靠读代码很难主动发现，得有条断言在背后盯着。

## 表4修复版本解析（从缺陷系统"备注"字段提取）
- 这个缺陷系统的版本号习惯是三段都是**个位数**（如 2.4.7、1.3.8），"备注"里测试确认修复时常用简写：
  - 完整写法：`1.2.0D`（跟"摘要"里 `#bugX.X.XA` 的版本前缀是同一套）
  - **三位数字简写**：`247B` = `2.4.7B`（每位数字对应版本号的一段，直接拆开加点）
  - **单字母简写**：备注只写一个字母（如 `D`、`E中修复`），意思是"跟发现版本同一个版本号，只是sub-build
    字母往后推了几位"——要读该bug的**发现版本**去掉末位字母当作版本根，再拼上备注里的新字母
    (发现版本 `2.3.0B` + 备注 `D` → 修复版本 `2.3.0D`)。单看备注本身完全猜不出版本号，必须联合发现版本。
  - **纯数字简写（无字母）**：如 `249001修复` = `2.4.9.001`（前3位是版本根三段拼一起，后面剩下的数字是
    第4段编号，不是字母）。这种因为没有字母标志、容易跟无关数字混淆，**必须用该bug自己的发现版本根做交叉
    校验**（前3位数字要能对上发现版本去掉字母、去掉点号之后的结果）才敢采信，光凭正则形状不够。
- **"备注"是多条带时间戳的日志追加而成**（`[人名 @ 时间] 内容`），要按这个格式切成条，只看**最后一条**——
  但如果全文（不只是最后一条）任何一条日志出现"仍存在/依旧/依然/未修复"这类否定词，说明这个bug当时被
  以为修好、后来验证发现没修好（例：`0090986` 备注唯一一条就是"B包问题仍存在"），这种整条都不填修复版本，
  即使"处理状况"字段显示"已修正"也不要信——按下不表比编错版本号安全。
- 正则写`(?:替换)?([A-Za-z])包?`时，**量词只作用于紧邻的单个字符/组**——写成`替换?`只让"换"变成可选，
  "替"变成必需，等于反着写反了。要让整个"替换"可选必须包一层非捕获组`(?:替换)?`。这个bug让所有单字母
  简写(`B中修复`这种)全部提取失败却不报错，是本次分析里最隐蔽的一个坑——**每次用`re.fullmatch`验证正则时
  一定要拿最简单的输入单独测一遍**（比如直接测`'B'`能不能匹配），不要只在完整流程里跑一遍就信。
- **`Review Submit Date` 不是"这条反馈什么时候来的"**。用户改旧评论时 Submit 保持首次提交时间（有 2017 年的），
  Last Update 才是本期活跃时间。**统计一律用 Last Update**。
- 同一条评论跨月 CSV 重复出现，按 `Review Link` 去重，保留 Last Update 最新的那条。
- **Device 列是 Google 设备代号**（pa3q / dm3q / e3q），不是营销名。
  → 完整映射在 Play Console → 设置 → 设备目录 → 导出 CSV，有 Device ID ↔ Marketing name。做一次 join 就能填满「机型名」列。
  没有映射时只能靠前缀判品牌（见 export_sheets.py 的 brand()）。

## 正则
- **`re.X`(VERBOSE) 会忽略正则里的空格**，导致所有含空格的模式静默失效。别用。
- **短关键词的子串误伤**，非拉丁语种尤其危险，全部要加词边界：
  | 关键词 | 误伤的词 | 结果 |
  |---|---|---|
  | `ави` (俄语AVI) | нр**ави**тся = 喜欢 | 纯好评判成"不支持AVI"，76条里71条是误报 |
  | `фон` (俄语背景) | теле**фон** = 手机 | — |
  | `seka` (斯洛伐克语卡顿) | 印尼语 bagus **seka**li = 非常好 | 夸奖判成卡顿，意思完全相反 |
  → 每次改词表后跑 `python3 <skill>/scripts/audit_keywords.py`，用 5★ 好评当阴性对照组自查。
- **`!!!` 不能当抱怨信号**。好评里同样大量出现（"Теперь лучший!!!"）。改用转折词（but/но/pero/但是/しかし…）。

## Google Sheets
- 表名不能写进 `--range`，要用 `--worksheet` 参数。写成 `"1_评论库!A1"` 会报
  `Unable to parse range: '1_评论库'!1_评论库!A1`。
- `horizontalAlignment` 用 `LEFT/CENTER/RIGHT`，**不是** Docs 的 `START/END`。
- `clear-values` 只清值保留格式；`reset` 才连格式一起清。数据行数变少时记得先清到足够大的范围。
- 分批写入时注意第一批含表头，起始行是 A1 不是 A2。
- GOOGLETRANSLATE 公式量大时会卡/超配额，只给需要的行加（当前只给 B 档）。

## 分类
- 长评论容易被次要关键词抢走主分类（R26340 讲 seek 卡顿被"字幕"抢走、R18015 讲音频被"下载器"抢走）。
  → 记进 `<project>/data/manual_override.json`。
- `primary=None` 但确实是问题的，说明 L1 词表没覆盖（例：R19419 讲搜索栏滚动惯性，没有"搜索"相关词）。
  → 补 L1 词表，或记 override。

## 公式列（新增）
- **写公式必须用 `value_input_option='USER_ENTERED'`**。gspread 的 `ws.update()` 默认 RAW，
  会把 `=IFERROR(GOOGLETRANSLATE(...))` 当**纯文本**写进去，格子里显示的就是公式字符串本身。
  skill 自带的 `write_sheet.py` 不支持这个参数 → 用 `scripts/upload.py` 或 `scripts/write_formula.py`。
- GOOGLETRANSLATE **异步计算**，写完立刻读会看到大片空白。等 30~60 秒再看，686 行能全部填满。
- 用 grep 过滤脚本输出时小心 `grep -v "^  "` —— 会把缩进的结果行一起滤掉，造成"没输出"的错觉。

## 设备代号（新增）
- Play Console 评论导出的 `Device` 是代号不是机型名 → 用 `~/.claude/shared/device-catalog`。
- **代号不唯一**（20551 个里 696 个一对多，多为同款换壳）。`lookup()` 按装机量取主匹配并置 `ambiguous`。
  例：`duchamp` = POCO X6 Pro 5G(24822) / Redmi K70E(120)；`sweet` = Redmi Note 10 Pro(37178) / ZTE Z839(6)。
- 别按代号前缀猜厂商。之前手写的 `brand()` 前缀规则把一批 vivo 机型归错，
  换成真实目录后 ISS-002 的 vivo 集中度从 5.6× 变 7.0×，ISS-006 还多出个 "Snapdragon 6/7" 的新信号。
- **`soc_family()` 比机型名更有分析价值**：同族芯片共享编解码器实现，按机型看是散的，按芯片族往往立刻收敛。

## 脚本里别硬编码列位置
改了表结构后 `row[10]` 从"置信度"变成了"应用版本"，导致 A 档人工翻译静默匹配不上（"人工 0 / 公式 686"）。
→ `upload.py` 已改成按表头名动态定位：`ci = {name: i for i, name in enumerate(head)}`。

## 加词边界时别写错正则
修 `seka` 子串误伤（印尼语 bagus **seka**li = 非常好）时，我写成 `\bseká?\b` ——
这是 "sek" + 可选的 "á"，**匹配不了原词 "seka"**，规则彻底失效，斯洛伐克语的真实卡顿反馈全漏了。
正确写法 `\bsek[aá]\b`。加边界后一定要两头验：**原词还能命中吗？误伤的词挡住了吗？**

## 「未分类」不等于「好评」
低星里未命中任何分类的评论，第一次统计 139 条中：真问题 ~72 / 纯好评误打低星 ~36 / 纯情绪 ~31。
**主体是词表没覆盖的真问题，不是好评**（84 条是 1 星）。所以不能拿"未分类"当好评筛子。
两件事分开修：① 噪音过滤加严（剔好评）② 补词表（捞真问题）。
补完后未分类 139 → 51，关联率 79.7% → 91.8%。

## 低星无信号判定
比穷举多语言好评词更鲁棒的规则：**低星 + 短文本(<45字符) + 不含抱怨信号 + 不含任何功能话题词 → 无效反馈**。
`excellent app` / `saludo de cuba` / `video player` 都会被拦，
而 `再生できない`（含抱怨信号）/ `동영상 화면이 안 나와요` 不会误杀。

## 强信号表里绝不能放「话题词」
补保加利亚语抱怨词时，我往 `complaint.STRONG` 里塞了 `реклам`（广告）。它是**话题词**不是故障词，
立刻出了两种错：① 俄语 `без рекламы`（**没有**广告，是夸奖）被判成抱怨；② 该评论被 5★ 门控放行进了问题库。
**铁律：`STRONG` 只放故障词（crash/не работает/无法播放），话题词一律归 `taxonomy.L1_KEYWORDS`。**
这和 `seka` 是同类错误——每次往词表加词，先问一句：这词出现在好评里正常吗？正常就不该加。

## 一级分类的优先级要按「谁更该被修」排
`UI与交互` 一开始放得太靠前，把「主要在讲解码问题、顺带说了句界面」的评论抢走了。
UI 抱怨通常是次要的 → 优先级排到最后。同理 `广告体验`/`付费` 也排在具体功能问题之后。

## 列号转字母不能用 chr(ord('A')+idx)
超过 Z 列（idx≥26）会得到 `[`、`\` 等垃圾字符，范围解析直接报
`Unable to parse range: '2_问题档案'![2:[300`。表2 现在有 27 列，正好踩中。

## L1_PRIORITY 是「谁排前面」不是「谁更对」——泛化词根会被静默抢主分类
XPlayer 一条俄语评论开头是「скачал и установил давно」（很久以前下载并安装了这个应用），
命中了"下载器"分类词根 `скача`；正文其实全是"几个月来部分 mp3 曲目开始播放报错"，命中了
"音乐播放器"。`L1_PRIORITY` 里"下载器"排在"音乐播放器"前面，主分类被判成了下载器，
一条播放报错证据混进了"下载器·笼统未细分" 35 条证据里，稀释了真实信号也污染了下载器的问题档案。
**根因不是关键词写错**（`скача` 匹配"下载/安装应用"和"下载视频功能"都是合理的词干匹配，
preflight 的"右侧粘连"警告本来就标了这条，但归类成"可能是故意词干匹配"没深究），**是"下载/安装
应用"这个通用开场白句式，天然会跟很多别的域共同出现在同一条评论里，而优先级表只按域本身的
重要性排，没考虑"这个词在句首当开场白 vs 在句中当实际功能点"的区别**。
**教训**：遇到"评论命中了不止一个 L1，但看内容明显该是另一个"时，别急着调整全局
`L1_PRIORITY` 顺序（牵一发动全身，会影响所有共现证据），先判断是不是"通用开场白词根撞上了
另一个域的实际内容词"这种模式——是就直接建新的更精确的二级分类去单独捞这类表达
（比如新增"音乐播放器::库内特定曲目播放报错"去精确匹配"播放报错"这个具体动作），
配合 `manual_override.json` 改这一条，不动全局优先级。

## 4-5★ 强信号词表覆盖不到「非常规措辞」的真实故障，会被整条丢弃
一条西语 4★ 评论写"最近好几次...弹出提示让我重启或返回，而我只是想直接播放歌曲"——这是
`trigger-surface.md` 里官方错误文案第三种（so库加载失败："Audio failed to load. Please
restart..."）的真实反馈，但因为表达方式（"sale msj de reiniciar el ir atrás"）没有命中
`complaint.STRONG` 里任何一条西语强信号正则（没有"no funciona/se cuelga"这类标准故障词），
在 4★ 门控（`star>=4 and not CMP.is_complaint()`）直接被判定成非投诉，`l1/l2/primary` 全部清空，
这条证据在分类结果里完全消失，不会出现在任何问题档案，也不会在"未分类率"里报警。
**跟"正则写错不报错"是同一类风险，但更隐蔽**——不是零命中会被 preflight 抓到，是"命中了
别的域词但被 4★ 门控拦住"，preflight 目前不检查这一步。**暂未修**：STRONG 列表是全局门控，
往里加"表达某个后果状态"（如"弹提示""让我重启"）风险比加故障词本身更大，容易引入新的误判，
需要更完整的回归检查（拿全量好评当阴性对照跑一遍），不要临时加一条就走。

## 生成复现步骤时要考虑「破解版/重打包 APK」这个干扰因素
用户提醒过一次：Play 商店的评论区不能保证留言的人用的都是官方渠道装的正版——有人装的是
第三方渠道重新打包/破解的 APK（去广告、解锁付费墙、绕过签名校验），出了问题照样跑到官方
评论区骂。这类破解包重新打包时最容易搞坏的东西——**ABI 不匹配、split APK 资源缺失、
安装包完整性**——跟"native so 库加载失败/提示重启应用"这类症状的常见诱因**几乎是同一个
技术画像**，没法从评论文本本身区分。
**怎么用**：不是每条证据都要往这个方向怀疑，重点看症状机制是否和"安装包本身完整性/签名/
资源缺失"高度重合（重启应用提示、启动即崩溃、特定 ABI 机型必现等）——机制吻合时，生成的
复现步骤里要加一步"先用 Play 商店官方渠道安装做基线，基线不复现再额外装一份第三方渠道版本
隔离测试对照"；如果只有非官方版本才复现，这条证据就不该算进官方 APK 的问题档案，应标记
"无法复现-挂起，疑似破解版干扰"，而不是当成"环境信息不足"稀里糊涂放进笼统池。
跟解码器逻辑本身关系更大的症状（比如"曲库里特定曲目报错""快进卡顿"）机制上跟破解版关系
不大（破解版通常不会去改音视频解码逻辑），不需要每次都测这个对照，别为了这条 gotcha
过度怀疑所有证据。
