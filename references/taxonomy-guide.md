# 为一个新 app 建分类体系

## 情况 A：用户已有分类体系（最理想）

直接对齐，**不要另造一套**。用户的体系通常是团队共识、和缺陷系统的模块划分对得上的。

拿到后做三件事：
1. 一级分类 → `L1_KEYWORDS` 的 key，每个配 15~40 条多语言话题词
2. 二级分类 → `L2_RULES` 的条目，配症状词
3. 跑一轮，把**数据里存在但体系没覆盖的**挑出来给用户看，问要不要新增

第 3 步很有价值。XPlayer 的实践中，用户给的 11 个一级分类没覆盖到：
稳定性崩溃、隐私与权限、安装更新、耗电发热、评分弹窗骚扰。
反馈后用户补了「应用性能」，又说「没有的你可以自己添加」，于是加了「UI与交互」「客服与响应」。

## 情况 B：用户没有现成体系（从数据里长出来）

**不要凭空设计分类**，要从真实评论里归纳。步骤：

1. 先只跑 `classify.py`（此时 taxonomy 还是模板，只有通用 7 类），产出 `data/classified.json`
2. 导出 1-3★ 非噪音评论，按长度降序，读前 300 条
3. 边读边记：用户在抱怨哪些**功能模块**（→ 一级），每个模块下有哪些**具体症状**（→ 二级）
4. 归纳成初稿给用户改——用户比你懂这个 app，他会调整命名和归并
5. 按初稿填 `taxonomy.py`，重跑，看未分类率

判断标准：**未分类率 < 10%** 就算够用了。剩下的长尾交给 `manual_override.json`。

## 一级分类的粒度

太粗（"播放问题"）→ 笼统池爆炸，没有定位价值
太细（"MKV 4K HDR 播放卡顿"）→ 每类只有 1-2 条证据，集中度算不出来

经验值：**一级 10~16 个，每个一级下 3~15 个二级**。
一级分类对应"哪个模块负责"，二级对应"提给开发时的一句话标题"。

## L1_PRIORITY 怎么排

一条评论命中多个一级分类时，主分类取靠前的。原则：

```
具体功能问题  >  应用性能/隐私  >  付费/广告  >  评分弹窗  >  UI
```

**为什么 UI 排最后**：UI 抱怨常是顺带提的。实测有条评论主要讲解码问题、末尾说了句"界面有点复杂"，
UI 优先级高时就被抢走了主分类。

**为什么广告/付费靠后**：它们是产品策略，不该压过功能缺陷。一条"广告多而且视频卡"的评论，
主分类应该是"卡顿"——那才是能修的。

## 写关键词的注意事项

**语言覆盖优先级**（按评论量）：英/西/阿/俄/印尼/葡/法/波斯/日/韩/土/中，
这 12 种约覆盖 85%。小语种靠 `manual_override` 兜底更划算。

**非拉丁语种必须加词边界**。血泪教训：
| 关键词 | 误伤 |
|---|---|
| `ави`(俄语AVI) | нр**ави**тся = 喜欢 |
| `фон`(俄语背景) | теле**фон** = 手机 |
| `seka`(斯洛伐克语卡顿) | 印尼语 bagus **seka**li = 非常好 |

加完边界要**两头验**：原词还能命中吗？误伤的词挡住了吗？
（`\bseká?\b` 看着对，其实是 "sek"+可选"á"，匹配不了原词 "seka"，规则彻底失效）

**加词前自问：这个词出现在好评里正常吗？**
正常 → 它是话题词，只能进 `L1_KEYWORDS`；绝不能进 `complaint.STRONG`。

## DOMAIN_TERMS 填什么

该 app 特有、能**缩小测试矩阵**的技术名词：
- 文件格式/编码：`mkv|avi|hevc|h.265|hdr10|dolby`
- 协议/连接：`chromecast|dlna|smb|rtmp`
- 具名功能：`A/B repeat|private folder|volume booster`

判断标准：看到这个词，测试能不能立刻知道该准备什么素材/什么环境？能就加。

## 改完之后

```bash
python3 <skill>/scripts/audit_keywords.py
```
它用 5★ 好评当**阴性对照组**——好评不该命中问题关键词，命中多的就是可疑规则。
输出里"高危"项若是话题词（quality/download），交给 complaint 门控即可，不用改；
若是子串误伤，必须加词边界。
